# SpecDD: Governance Enforcement Specification

This specification outlines the automated, deterministic validation gates that enforce standard compliance without slow enterprise meetings or approvals.

---

## 🌿 1. Git Workflow Gates
* **Default Branch Protection**: Direct commits to the `main` branch are blocked. Integration occurs via the `develop` branch.
* **Pull Request Audit**: Merge permissions to stable branches require successful runs of the automated validator suite in Github Actions CI.

---

## ⚡ 2. Pre-Commit Verification Pipeline
Before committing code locally, developers must run structural standards checks:
```bash
# Run schema and directory checks
python validation/bin/validate-repo.py --target ./ --audit --observability
```
If the script emits error code `1`, the developer's Git commit action is automatically cancelled.

---

## 🧪 3. Validation-First Pull Request Workflow

To maintain absolute feature integrity and prevent regression bugs, all codebases must enforce a **Validation-First** delivery pattern:

1. **Assertion Definition (Red Phase)**: Write unit tests, mock telemetry assertions, or CLI test wrappers *prior* to modifying any application logic.
2. **Verify Failure**: Run the validation assertions on the unchanged codebase to verify they fail. This guarantees that the validations are actively checking the new behaviors.
3. **Feature Implementation (Green Phase)**: Write the minimal clean source code required to satisfy the assertions.
4. **Local Verification Check**: Run the repository validator suite locally to ensure compliance:
   ```bash
   python validation/bin/validate-repo.py --target ./ --audit --observability
   ```
5. **CI Block Gates**: Pull Request integration pipelines in GitHub Actions will run these validation checks automatically. PRs will be blocked from merging if code changes are integrated without matching validation logic or if `validate-repo.py` returns error code `1`.

---

## 🏷️ 4. Semantic Versioning

Release tags must follow strict semver parameters:
* **Patch releases (`vX.Y.Z`)**: Non-breaking bug fixes or visual upgrades.
* **Minor releases (`vX.Y.0`)**: Backwards-compatible new features.
* **Major releases (`vX.0.0`)**: Breaking database changes or core framework updates.
* **Release trigger**: Auto-generated by CI when pull requests merge successfully into the `main` branch.
